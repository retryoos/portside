# Architecture

> System design, stack choices, and deployment for the 12-hour MVP. Every choice here is biased toward "what gets a clean five-minute demo at 19:00 with three engineers."

---

## 1. System diagram (in words)

```
┌──────────────────────────────────────────────────────────────────────┐
│                          Browser (demo laptop)                       │
│  Next.js 15 + Tailwind + shadcn/ui                                   │
│  Three-panel UI: documents | timeline+table | claim packet           │
└──────────────┬───────────────────────────────────────────────────────┘
               │ HTTP (single JSON contract)
               ▼
┌──────────────────────────────────────────────────────────────────────┐
│                       FastAPI backend (async)                        │
│                                                                      │
│   POST /voyages         → upload PDFs, kicks off pipeline            │
│   GET  /voyages/{id}    → poll pipeline state + final result         │
│   (letter PDF is generated client-side from the letter HTML —        │
│    no backend export endpoint needed; see §3 PDF export)             │
│                                                                      │
│   Pipeline orchestrator (async, in-process):                         │
│      Agent 1 → Agent 2 → Agent 3 → Agent 4                           │
│      (with Agent 3 starting as soon as Agent 1 finishes,             │
│       Agent 2 running in parallel; Agent 4 awaits both)              │
└──────────────┬───────────────────────────────────────────────────────┘
               │
               ▼
┌──────────────────────────────────────────────────────────────────────┐
│   pdfplumber (local, MIT)  →  Anthropic API — Claude Sonnet 4.6      │
│                                                                      │
│   - PDF text + table extraction happens locally before any LLM call  │
│   - Tool-use with strict JSON schema for extraction (Agent 1)        │
│   - Classification for laytime exceptions (Agent 2a)                 │
│   - Reasoning for dispute analysis (Agent 3)                         │
│   - Streaming generation for the claim letter (Agent 4)              │
│   - Opus 4.7 held in reserve as a per-agent quality escape hatch     │
│   - Native Claude PDF input used only as fallback for scanned docs   │
└──────────────────────────────────────────────────────────────────────┘
```

No database. No queues. No auth. No deploy. In-memory state, one process, run locally on the demo laptop.

## 2. Data flow

1. Browser POSTs three PDFs to `/voyages` along with a `perspective` flag (`"owner"` or `"charterer"`).
2. Backend assigns a `voyage_id`, returns it immediately, kicks off the async pipeline.
3. Browser polls `/voyages/{id}` every 500ms.
4. Backend returns the current pipeline state: `{stage: "extracting" | "calculating" | "analyzing" | "drafting" | "done", partial_result: {...}}`.
5. As each agent finishes, its output is merged into `partial_result` and visible to the polling browser. This is what powers the "live agent steps" UI animation.
6. When `stage: "done"`, browser shows full table, narrative, and quantum.
7. User clicks **Generate Claim Letter** — the backend has already returned the letter content (HTML/markdown segments) in the `VoyageState`; the frontend renders it inline and a **Download PDF** button generates the PDF client-side from that HTML (`html2pdf.js` or a print stylesheet). No backend PDF endpoint, no server-side rendering library.

## 3. Stack choices and why

| Layer        | Choice                                          | Why                                                                                              |
| ------------ | ----------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Frontend     | Next.js 15 (App Router) + Tailwind + shadcn/ui  | Fast to build, looks professional, three engineers already know it                               |
| Backend      | FastAPI + uvicorn, Python 3.12                  | Async-first, plays well with Anthropic SDK, fastest path to a typed HTTP API                     |
| LLM          | Anthropic Claude **Sonnet 4.6** for every agent | ~5× cheaper than Opus 4.7 on input and output; meaningfully lower latency. Opus 4.7 held in reserve as a per-agent quality escape hatch — flip a single agent via `ANTHROPIC_MODEL_PRIMARY` if writing quality fails at the 16:00 polish round. |
| PDF parsing  | **`pdfplumber`** (MIT, pure Python) primary; Claude native PDF input as fallback | Local text + table extraction strips the vision-token surcharge and most of the latency from Agent 1. Our synthetic PDFs are text-native (generated by `weasyprint`) — pdfplumber extracts them with full fidelity. Native PDF input kicks in only if pdfplumber returns empty (scanned/unparseable). |
| PDF export   | **Client-side** — `html2pdf.js` or browser print stylesheet on the rendered letter HTML | No native dependencies anywhere (no cairo/pango), nothing to install on Windows, nothing to apt-install on App Runner. The letter is already HTML in the right panel; we export it where it lives. |
| Word export  | Optional / cuttable. If wanted, `docx` (JS, client-side) from the same HTML | Keeps everything client-side and Windows-clean. `python-docx` on the backend is the fallback only if a JS path proves fiddly. |
| Synthetic data PDFs | `weasyprint` (HTML → PDF) — **dev-time only** | Used once, by the synthetic-data background workstream, to generate the input CP/NOR/SoF PDFs. Runs on a Mac or WSL, never in production, never on Windows-native, never on App Runner. This is the *only* surviving use of weasyprint. |
| State        | In-memory dict, keyed by `voyage_id`            | Hackathon. No persistence. Restart kills state — accept it.                                      |
| Deployment   | **Local laptop is the demo (primary).** In parallel: frontend → **AWS Amplify Hosting**, backend → **AWS App Runner** as a live "and it's on AWS right now" flex | Local demo removes DNS/TLS/env failure modes on stage. The AWS deploy is built by a background workstream, never on the critical path, and earns sponsor credit + a real URL. No auth, no DB on the day. See §12. |
| Bundler/Build| Default Next.js dev server                      | Don't waste time on `next build`.                                                                |

## 4. Anthropic SDK usage

Use **prompt caching** on the Charter Party text in every call after Agent 1 — the CP clause language is the same across Agents 2/3/4 and will hit cache.

Use **tool use with `strict: true`** for Agent 1 extraction. The JSON schema is the contract.

Use **streaming** in Agent 4 so we can render letter content into the right panel as it generates (visual drama for the demo).

For Agent 2's classifier step, use the **batch tool-use pattern**: one call that classifies all SoF events at once into a list, not one call per event. Latency matters.

## 5. Latency budget

Total target: **end-to-end under 25 seconds** on three demo documents (with pdfplumber + Sonnet 4.6).

| Stage                       | Budget       |
| --------------------------- | ------------ |
| PDF upload + handoff        | 1s           |
| pdfplumber text extraction  | <1s          |
| Agent 1 (extraction, text)  | 4s           |
| Agent 2 LLM classification  | 4s           |
| Agent 2 Python arithmetic   | <0.1s        |
| Agent 3 (dispute analysis)  | 6s (parallel with 2 when possible) |
| Agent 4 (drafting, streamed)| 7s           |
| Buffer                      | 3s           |
| **Total**                   | **~22s**     |

If we exceed 35s on the demo run, the prompt cache is missing — check that the cross-cutting prefix is cached. If we exceed 45s, something is wrong with the network — switch to phone hotspot.

## 6. Concurrency model

```
T=0     pdfplumber extracts text from all 3 PDFs (<1s, parallel processing)
T=1     Agent 1 starts (extraction, single Sonnet call with text)
T=5     Agent 1 done → fan out:
          Agent 2 starts (LLM classifier on SoF events)
          Agent 3 starts (dispute analysis on extracted CP + SoF)
T=9     Agent 2 LLM done → Python arithmetic
T=9.1   Agent 2 done
T=11    Agent 3 done
T=11    Agent 4 starts (claim drafter, streamed)
T=18    Agent 4 done
```

Agent 2 and Agent 3 run in parallel via `asyncio.gather`. Agent 4 awaits both.

## 7. Failure handling

It is a hackathon. The failure handling is: **the demo path works on the demo scenario.** Outside the demo scenario, we expose errors honestly and move on.

That said:
- Wrap every LLM call in a 30-second timeout. On timeout, retry once with Sonnet.
- If Agent 1 extraction returns malformed JSON (rare with tool-use + strict mode but possible), retry once with a tightened prompt.
- If Agent 2's Python arithmetic blows up on unexpected input, log the inputs and surface a "calculation error" badge in the UI. Do not crash.
- Backend exception → frontend gets `{stage: "error", message: ...}`. Render it inline. Move on.

## 9. Configuration

Single `.env` file at the API root:
```
ANTHROPIC_API_KEY=...
ANTHROPIC_MODEL_PRIMARY=claude-sonnet-4-6
ANTHROPIC_MODEL_ESCAPE=claude-opus-4-7   # per-agent quality escape hatch only
```

No other config. No feature flags.

## 10. Running locally (for the demo)

Two terminals:

```bash
# Terminal 1
cd apps/api
uv sync
uv run uvicorn portside_api.main:app --reload --port 8000

# Terminal 2
cd apps/web
pnpm install
pnpm dev   # http://localhost:3000
```

Frontend talks to `http://localhost:8000` directly. CORS allowlist `http://localhost:3000` **and** the Amplify domain (see §12).

## 11. What we are explicitly NOT building in the architecture

- Authentication (deferred to Phase C)
- Database (in-memory for the day)
- Background workers / queues
- File storage beyond `/tmp`
- Multi-tenant anything
- Server-side PDF rendering (PDF is client-side; no cairo/pango anywhere)
- Observability beyond `print()`
- Any kind of webhook, integration, or third-party connector
- Email send

All of these are roadmap. None of them ship on May 28th.

## 12. Hackathon-day AWS deployment (parallel flex, off the critical path)

**The local laptop is the demo. AWS is the "and it's already live" flex** — it earns sponsor credit (AWS sponsors this hackathon) and gives a real URL to show judges, but it must never block the demo. A background workstream owns it; if it breaks, the demo is unaffected.

```
Browser ──► AWS Amplify Hosting (Next.js 15 frontend)
                    │ HTTPS
                    ▼
            AWS App Runner (FastAPI container, scales to zero)
                    │
                    ▼
            Anthropic API (Sonnet 4.6)
```

- **Frontend → AWS Amplify Hosting.** Supports Next.js 15 App Router (SSR). Connect the GitHub repo, set `apps/web` as the app root, set `NEXT_PUBLIC_API_URL` to the App Runner URL. Budget 30–45 min for first-deploy build-setting gotchas.
- **Backend → AWS App Runner.** A small Dockerfile (`python:3.12-slim` base — note: **no cairo/pango needed anymore**, because PDF export is client-side). Push to ECR or use App Runner's source deploy. Set `ANTHROPIC_API_KEY`. Scales to zero (~$5–15/mo against the $200 credit).
- **No auth, no DB, no S3 on the day.** In-memory state is fine; App Runner runs a single instance for the demo.
- **CORS:** the FastAPI app must allowlist the Amplify domain in addition to `localhost:3000`.

This is **Phase B-lite** — a strict subset of the Phase C deploy in [extended_plan.md §10](extended_plan.md#10-phase-c--taking-portside-to-the-startup-contest-the-week-after). Phase C adds Supabase auth + DB, a custom domain, CI/CD, and observability. None of that is on May 28th.
